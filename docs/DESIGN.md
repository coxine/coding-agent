# 编程智能体总体设计文档

## 1. 文档目的

本项目实现一个可在终端中交互使用的编程智能体。产品形态参考 Codex CLI 和 OpenCode：用户在 TUI 中输入编程任务，智能体调用 OpenAI 兼容模型，自主读取和修改工作区文件、执行本地命令，并持续迭代直到完成任务或触发终止条件。

本文只定义总体方案、基本功能和模块边界，不包含具体实现代码。

## 2. 项目目标

项目需要形成一个完整、可解释、可独立运行的最小编程智能体，核心目标如下：

1. 提供基于 TypeScript 的终端用户界面。
2. 通过 OpenAI 兼容 API 调用支持原生 tool calling 的模型。
3. 自行实现对话历史、上下文管理、工具定义与本地执行、模型响应解析、Agent 循环、终止条件和错误处理。
4. 允许智能体在指定工作目录内读取、搜索、创建和修改文件，并执行命令。
5. 清晰展示模型回复、工具调用、执行结果、错误和当前状态。
6. 对越界文件访问和高风险命令进行限制或请求用户确认。

## 3. 非目标

第一版不包含以下能力：

- Web 或桌面图形界面。
- 多智能体协作。
- 浏览器自动化和远程计算机控制。
- 向量数据库或代码语义索引。
- 插件市场和第三方 Agent 框架。
- 服务端托管的代码执行、文件管理或会话管理。
- 自动执行 Git push、发布、部署等外部副作用操作。
- 同时编辑多个独立工作区。

## 4. 总体架构

项目采用前后端分离的本地进程架构。TUI 使用 TypeScript、React 与 Ink；Agent Core 使用 Python：

```text
┌──────────────────────────────────────────────┐
│ TypeScript TUI                              │
│ 输入、消息展示、工具卡片、确认弹窗、状态栏 │
└──────────────────────┬───────────────────────┘
                       │ JSON Lines / stdio
┌──────────────────────▼───────────────────────┐
│ Python Agent Core                            │
│ 会话、模型客户端、Agent 循环、上下文、工具  │
└───────────────┬──────────────────┬───────────┘
                │                  │
       OpenAI-compatible API   Local Workspace
                               文件系统 / Shell
```

### 4.1 TypeScript TUI

TUI 只负责交互和展示，不包含 Agent 决策逻辑。主要职责：

- 获取用户输入并发送给 Agent Core。
- 流式展示模型输出。
- 展示工具名称、参数、运行状态和结果摘要。
- 展示文件修改 diff。
- 在高风险操作前请求用户确认。
- 支持取消当前任务和退出程序。
- 展示模型、工作目录、当前轮数和运行状态。

### 4.2 Python Agent Core

Agent Core 是项目的核心，主要职责：

- 管理会话和消息历史。
- 构造系统提示词与工具定义。
- 调用 OpenAI 兼容 API。
- 解析文本、流式增量和 tool calls。
- 校验并执行本地工具。
- 将工具执行结果追加到对话历史。
- 驱动多轮 Agent 循环并判断何时结束。
- 管理上下文长度、输出截断和错误恢复。
- 向 TUI 发送结构化事件。

### 4.3 进程通信

TUI 启动 Python Core 子进程，双方通过标准输入输出传输一行一个 JSON 对象的事件。日志必须写入标准错误，避免污染协议数据。

采用 JSON Lines 的原因：

- 无需额外启动本地服务或占用端口。
- 容易调试、记录和回放。
- TypeScript 与 Python 都可直接处理。
- 支持流式事件和长期运行的 Agent 循环。

## 5. 基本功能清单

### 5.1 启动与配置

- 从当前目录或命令行参数确定工作区根目录。
- 从环境变量读取 API Key、Base URL 和模型名称。
- 启动时校验 Python、Node.js、配置和工作目录。
- API Key 不写入日志、TUI、仓库或会话记录。
- 缺少必要配置时给出可理解的错误提示。

建议的环境变量：

```text
OPENAI_API_KEY
OPENAI_BASE_URL
AGENT_MODEL
```

### 5.2 TUI 交互

基础界面由以下区域组成：

1. 顶部信息栏：项目名称、模型、工作目录。
2. 会话区：用户消息、模型回复和工具执行记录。
3. 输入区：支持多行任务输入和提交。
4. 状态栏：显示思考中、调用工具、等待确认、完成或失败。

必须支持的交互：

- 提交新的编程任务。
- 查看模型的流式回复。
- 展开或折叠工具调用详情。
- 对需要确认的操作选择允许或拒绝。
- 取消当前运行中的任务。
- 退出程序。

### 5.3 模型调用

- 使用 OpenAI 兼容接口，具体请求差异由模型适配层封装。
- 向模型提供原生 tool calling 定义。
- 支持流式文本输出。
- 正确关联每个 tool call 与对应的 tool result。
- 对参数 JSON 解析失败、响应中断、限流和网络错误进行处理。
- Base URL、模型名和 API Key 均可配置，不在业务逻辑中硬编码。

### 5.4 Agent 循环

一次用户任务对应一个 Agent turn，基本循环如下：

1. 接收用户任务并加入消息历史。
2. 组合系统提示词、历史消息和工具定义。
3. 请求模型响应。
4. 如果模型返回文本，则流式发送给 TUI。
5. 如果模型请求工具，则校验并执行工具。
6. 将工具结果加入消息历史并再次请求模型。
7. 模型给出最终回答后结束本轮任务。

必须实现的终止条件：

- 模型返回最终回答且没有后续工具调用。
- 达到最大 Agent 步数。
- 连续出现重复且无进展的工具调用。
- 用户主动取消。
- 连续 API 或协议错误达到上限。
- 出现无法恢复的内部错误。

### 5.5 本地工具

第一版提供以下六个工具：

#### `list_directory`

- 列出指定目录下的文件和子目录。
- 支持限制返回数量。
- 不递归读取整个仓库。

#### `read_file`

- 读取 UTF-8 文本文件。
- 支持按行范围读取。
- 返回行号。
- 对大文件进行分段和长度限制。

#### `search_text`

- 在工作区中搜索文件名或文本内容。
- 默认忽略 `.git`、依赖目录和构建产物。
- 返回文件路径、行号和匹配摘要。

#### `write_file`

- 创建新文本文件或完整覆盖已有文本文件。
- 写入前验证路径。
- 覆盖已有文件前生成变更信息。

#### `apply_patch`

- 对已有文件进行局部修改。
- 修改失败时返回明确原因，不产生部分写入。
- 成功后返回修改摘要或 diff。

#### `run_command`

- 在工作区内运行非交互式命令。
- 返回退出码、标准输出、标准错误和是否超时。
- 支持超时、输出长度限制和用户取消。
- 不允许命令静默改变工作目录边界。

### 5.6 工具执行结果

所有工具都返回统一结构，至少包含：

```json
{
  "ok": true,
  "toolCallId": "call_123",
  "summary": "Read 80 lines from src/main.py",
  "data": {},
  "error": null
}
```

失败时必须包含稳定的错误类型，例如：

- `invalid_arguments`
- `path_outside_workspace`
- `file_not_found`
- `permission_denied`
- `command_timeout`
- `command_failed`
- `cancelled`
- `internal_error`

工具错误应返回给模型，由模型决定修正参数、选择其他工具或向用户解释，而不是直接导致整个程序崩溃。

### 5.7 对话与上下文管理

- 保存当前运行期间的完整消息序列。
- 区分 system、user、assistant 和 tool 消息。
- 保留 tool call ID 及其对应结果。
- 不在启动时读取整个仓库，由模型按需调用工具获取上下文。
- 对过长的文件内容、搜索结果和命令输出进行截断。
- 始终保留系统规则、用户原始任务、最近消息和未完成工具调用。
- 第一版只要求单次程序运行期间保持会话，不要求跨进程持久化。

### 5.8 文件变更展示

- 文件写入或补丁成功后生成统一 diff。
- TUI 默认展示修改摘要，可展开查看完整 diff。
- Agent 最终回复应概括修改内容和验证结果。
- 第一版不自动提交 Git commit。

### 5.9 权限与安全

- 所有文件路径解析为绝对路径后，必须仍位于工作区根目录下。
- 默认禁止读取 `.env`、私钥、凭据和 Git 内部对象。
- 命令执行前进行风险分类。
- 读取、搜索、普通测试和构建命令可直接执行。
- 删除文件、覆盖重要配置、安装依赖和其他高风险命令需要用户确认。
- Git push、发布、部署和访问工作区外文件默认禁止。
- 对命令设置执行超时和输出上限。
- 用户取消后终止当前模型请求或本地子进程。

### 5.10 错误处理

- API 临时错误允许有限次数、带退避的重试。
- 参数或协议错误向 TUI 展示，并记录到当前运行状态。
- 工具执行失败不得破坏 Agent 的消息结构。
- Python Core 异常退出时，TUI 显示退出原因和建议处理方式。
- TUI 异常退出时，应终止其启动的 Python 子进程。
- 错误日志不得包含 API Key 或完整敏感配置。

## 6. TUI 状态模型

TUI 至少区分以下状态：

```text
idle
  └─> requesting_model
        ├─> streaming_response
        ├─> running_tool
        ├─> waiting_for_approval
        ├─> completed
        ├─> failed
        └─> cancelled
```

同一时刻只运行一个用户任务。任务执行期间可以取消，但不能并行提交第二个任务。

## 7. TUI 与 Core 的基础事件

### 7.1 TUI 发给 Core

- `initialize`：初始化工作区和模型配置。
- `submit_task`：提交用户任务。
- `approval_response`：允许或拒绝待确认操作。
- `cancel_turn`：取消当前任务。
- `shutdown`：正常退出。

### 7.2 Core 发给 TUI

- `initialized`：初始化完成。
- `turn_started`：任务开始。
- `agent_status`：Agent 阶段和 step 更新。
- `assistant_message_started`：创建一条流式模型消息。
- `assistant_delta`：模型文本增量。
- `assistant_message_finished`：模型消息流结束。
- `tool_requested`：模型请求工具。
- `approval_required`：工具需要用户确认。
- `tool_started`：工具开始执行。
- `tool_output_delta`：长时间命令的受限实时输出。
- `tool_finished`：工具执行完成。
- `file_diff`：文件变更内容。
- `context_updated`：上下文或输出被截断、压缩。
- `turn_finished`：任务正常结束。
- `turn_failed`：任务执行失败。
- `turn_cancelled`：任务已取消。
- `error`：发生错误。
- `shutdown_complete`：Core 已完成清理并可退出。

所有事件都应包含事件类型、会话 ID、任务 ID 和时间戳；工具相关事件还应包含 tool call ID。

## 9. 环境与版本管理

### 9.1 uv

`uv` 管理 Python 版本、虚拟环境、Python 依赖和锁文件：

- 项目依赖写入 `pyproject.toml`。
- 精确版本解析写入 `uv.lock`。
- Python Core 和 Python 测试均通过 `uv run` 启动。
- 不提交 `.venv`。

### 9.2 npm

`npm` 管理 TypeScript TUI 依赖和脚本：

- TUI 依赖写入 `apps/tui/package.json`。
- 提交 `package-lock.json` 保证可复现安装。
- 根目录提供统一的开发、构建、测试和启动脚本。
- 不提交 `node_modules` 和构建产物。

### 9.3 Git

Git 用于版本控制和保留真实开发过程：

- 在题目发布后新建公开仓库。
- 按功能拆分提交，不压缩或改写已推送历史。
- 不提交 API Key、`.env`、缓存、依赖目录和录制素材。
- 截止时间后不再向提交仓库推送新 commit。

## 10. 配置优先级

配置从高到低按以下顺序解析：

1. 命令行参数。
2. 环境变量。
3. 非敏感的项目配置文件。
4. 程序默认值。

API Key 只能通过环境变量或未入库的本地配置提供。`.env.example` 只保留变量名和说明，不包含真实值。

## 11. 最小验收标准

第一版完成时必须能演示以下完整流程：

1. 在一个已有代码项目中启动 TUI。
2. 用户输入一个真实编程任务。
3. 模型通过工具查看目录、读取和搜索代码。
4. 模型调用补丁或写入工具修改文件。
5. TUI 展示工具过程和文件 diff。
6. 模型执行测试或构建命令。
7. 如果测试失败，模型读取错误并再次修改。
8. 测试通过后，模型输出最终总结并结束循环。
9. 用户可以在执行期间取消任务。
10. 越界路径和高风险操作被拒绝或要求确认。

## 12. 关键设计决策

### 为什么 TUI 使用 TypeScript

TypeScript 适合构建事件驱动、组件化的终端界面，能将消息列表、工具状态、输入框和确认交互拆成清晰组件。UI 与 Agent Core 分离后，界面变化不会影响核心决策逻辑。

### 为什么 Agent Core 使用 Python

Python 适合实现模型交互、文件工具、子进程控制和测试逻辑。使用 `uv` 可以快速建立可复现环境，也便于清晰展示哪些核心逻辑由项目自行实现。

### 为什么使用独立进程和 JSON Lines

这使 TypeScript 与 Python 保持低耦合。协议事件可以直接记录和测试，Core 也可以在不启动 TUI 的情况下单独运行集成测试。

### 为什么不把整个项目直接放进上下文

大多数文件与当前任务无关。让模型通过工具按需读取可以减少上下文消耗，也能保留清晰、可检查的操作过程。
